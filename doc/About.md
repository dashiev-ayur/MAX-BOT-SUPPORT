# MAX Bot: логика работы системы поддержки с несколькими менеджерами

## Назначение

Бот для мессенджера MAX, реализующий сценарий «один вопрос покупателя → видят все менеджеры → отвечают все, кто хочет».  
Ключевое требование: менеджеры видят, кто уже ответил и что именно. 
Покупатель видит ответы всех менеджеров.

---

## Роли и участники

| Роль | Права и поведение |
|------|-------------------|
| **Покупатель** | Отправляет вопрос боту. Получает уведомления об ответах всех менеджеров. Не видит других покупателей. |
| **Менеджер** | Получает все новые вопросы. Может отвечать на любой. Видит уведомления «кто уже ответил и что написал». |
| **Бот** | Принимает вебхуки, маршрутизирует сообщения, хранит состояние в SQLite, рассылает уведомления. |

---

## Структура данных (БД: SQLite)

### `questions` — вопросы покупателей

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | TEXT (PK) | UUID вопроса |
| `client_user_id` | INTEGER | ID покупателя |
| `client_name` | TEXT | Имя покупателя |
| `text` | TEXT | Текст вопроса |
| `created_at` | DATETIME | Время создания (DEFAULT CURRENT_TIMESTAMP) |

### `manager_messages` — сообщения с вопросами, отправленные менеджерам

| Поле | Тип | Описание |
|------|-----|----------|
| `msg_mid` | TEXT (PK) | MID сообщения в MAX (уникальный идентификатор сообщения) |
| `question_id` | TEXT | Ссылка на вопрос (FK → questions.id) |
| `manager_id` | INTEGER | Кому отправлено |

### `answers` — ответы менеджеров

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | TEXT (PK) | UUID ответа |
| `question_id` | TEXT | На какой вопрос ответ |
| `manager_id` | INTEGER | Кто ответил |
| `manager_name` | TEXT | Имя менеджера (для отображения) |
| `answer_text` | TEXT | Текст ответа |
| `created_at` | DATETIME | Время ответа |

> **Важно:** вопрос остаётся «открытым» всегда. Нет статусов типа `open/closed`. Все ответы сохраняются и отображаются.

## Поток обработки событий

### 1. Покупатель нажимает «Начать» (`bot_started`)

- Бот проверяет: отправитель — не менеджер.
- Отправляет приветственное сообщение покупателю.
- Возвращает `200 OK` без изменения БД.

### 2. Покупатель пишет вопрос (`message_created`)

1. Генерируется `questionId = randomUUID()`.
2. Вопрос сохраняется в `questions`.
3. Для каждого менеджера формируется сообщение «Новый вопрос от …» и отправляется через API MAX.
4. MID каждого отправленного сообщения сохраняется в `manager_messages` (связь: `msg_mid → question_id → manager_id`).
5. Покупателю отправляется подтверждение: «Ваш вопрос передан менеджерам».

### 3. Менеджер отвечает через Reply на сообщение с вопросом

1. Бот проверяет, что сообщение — это Reply (`link.type === 'reply'`).
2. По `msg_mid` из Reply находится `question_id` в `manager_messages`.
3. По `question_id` загружается исходный вопрос из `questions`.
4. Ответ менеджера отправляется покупателю: `💬 <Имя>: <текст>`.
5. Ответ сохраняется в `answers`.
6. Остальным менеджерам рассылается уведомление: «<Имя> ответил на вопрос от <покупатель>. Ответ: <текст>».
7. Любой другой менеджер может ответить позже — его ответ тоже уйдёт покупателю и вызовет новое уведомление для остальных.

### 4. Менеджер пишет не через Reply

- Бот отвечает: «⚠️ Используйте Reply на сообщение с вопросом, чтобы ответить покупателю».
- Ничего не сохраняется и не рассылается.

## Диаграмма потоков (текстовая)

Покупатель → [вопрос] → Бот → [создаёт questionId] → questions
↓
для каждого менеджера:
→ sendToUser(manager)
→ manager_messages (msg_mid, question_id, manager_id)
↓
Покупатель: «вопрос передан»

Менеджер → [Reply на вопрос] → Бот
↓
проверка: link.type === 'reply'
поиск question_id по msg_mid
↓
Отправка ответа покупателю
Сохранение в answers
Рассылка уведомлений остальным менеджерам

## Особенности реализации

- **Конкурентность:** SQLite работает в режиме WAL (`journal_mode = WAL`) для лучшей производительности при одновременных ответах нескольких менеджеров.
- **Идемпотентность вебхуков:** обработка не создаёт дубликатов при повторных вызовах, так как ключевые сущности (вопросы и ответы) создаются только один раз, а уведомления отправляются на основе данных из БД.
- **Связь по MID:** все уведомления менеджерам привязаны к исходному сообщению (MID). Если менеджер отвечает на это сообщение, бот точно знает, к какому вопросу относится ответ.
- **Отсутствие блокировки:** нет флага «вопрос закрыт». Любой менеджер может ответить в любой момент.

## Примеры сценариев

### Сценарий 1: Один менеджер ответил

- Покупатель: «Можно оплатить картой?»
- Бот: «Ваш вопрос передан менеджерам»
- Менеджер Анна (Reply): «Да, оплата картой доступна»
- Бот: отправляет покупателю «💬 Анна: Да, оплата картой доступна» и сохраняет ответ.
- Бот: уведомляет Бориса и Виктора: «Анна ответила: Да, оплата картой доступна».

### Сценарий 2: Два менеджера ответили

- Менеджер Борис (Reply): «Также принимаем СБП»
- Бот: отправляет покупателю «💬 Борис: Также принимаем СБП».
- Бот: уведомляет Виктора: «Борис ответил: Также принимаем СБП».
- Покупатель видит оба ответа.

### Сценарий 3: Менеджер пишет мимо Reply

- Менеджер Виктор: «Уточните, пожалуйста, город доставки» (не через Reply)
- Бот: отвечает Виктору «⚠️ Используйте Reply на сообщение с вопросом…»
- Покупатель не получает это сообщение.

## Ограничения и допущения

- **API MAX:** предполагается, что `POST /messages?user_id=...` корректно доставляет сообщения и возвращает `message.body.mid`.
- **Reply:** используется стандартный механизм Reply в MAX. Если он не сработает, бот не сможет корректно связать ответ менеджера с вопросом.
- **Производительность:** SQLite подходит для небольшого и среднего объёма (до десятков тысяч вопросов в месяц). При росте нагрузки рекомендуется перенести БД на PostgreSQL.
- **Консистентность уведомлений:** если API MAX временно недоступен, часть уведомлений может не уйти. Для продакшена стоит добавить очередь сообщений (например, Redis/RabbitMQ) и retry.

## Расширения и улучшения

- **История ответов для менеджера:** команда `/history` показывает все ответы по вопросу.
- **Таймаут-напоминание:** если за N минут никто не ответил, бот пингует всех менеджеров повторно.
- **Теги/категории вопросов:** можно добавить поле `category` в `questions` и фильтровать вопросы по темам.
- **SLA и метрики:** хранить время первого ответа, среднее время ответа, количество ответов на вопрос.
- **Мультитенантность:** добавить `tenant_id` в таблицы и фильтровать по нему, чтобы один инстанс бота обслуживал несколько компаний.
